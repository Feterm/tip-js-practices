## 3. Функции, ссылки и копирование

Прогноз заполняется до первого запуска. Для эксперимента 2 необходимо
сохранить исходный результат и отдельно указать результат после исправления.

| № | Прогноз до запуска | Фактический результат | Причина |
|---:|---|---|---|
| 1 | `sum(2, 3)` = 5 (число); `sum("2", 3)` = 23 (строка) | `5` (number); `23` (string) | `+` с числами складывает, а если первый аргумент строка - будет конкатенация, функция сама ничего не приводит к числу |
| 2 | Без return функция вернёт `undefined` | До правки: `undefined`. После правки: `16` | В теле стрелочной функции с `{}` вычисление `value * value` просто выполняется и никуда не возвращается - нужен явный `return` |
| 3 | `product.stock` = 5; `product === alias` = true | `5`; `true` | `alias` это не копия, а второе имя того же объекта, поэтому изменение через alias видно и в product |
| 4 | `products[0].stock` = 7; `products === copy` = false; `products[0] === copy[0]` = true | `7`; `false`; `true` | spread скопировал массив (новый copy), но объект внутри массива остался тот же самый - копия поверхностная |
| 5 | `product.stock` = 3; `first.stock` = 8; `second.stock` = 3 | `3 8 3` (в одну строку) | Порядок свойств важен: в first `stock: 8` идёт после `...product` и побеждает, а в second наоборот - `...product` затирает stock обратно на 3 |

Добавил `return` перед выражением - теперь `square(4)` возвращает `16`. Оба варианта видно в файле `examples/functions-and-references.js` (в комментарии описано, что было не так).

## 4. Модель данных и функции

Задача - это объект с четырьмя полями:

```js
{ id: 20, title: "Подготовить демонстрацию", completed: false, priority: "medium" }
```

- `id` - положительное целое число, безопасное (`Number.isSafeInteger`), уникальное в пределах списка.
- `title` - строка, после `trim()` длина от 1 до 100. Внутренние пробелы не трогаем.
- `completed` - строго `true`/`false`, у новой задачи всегда `false`.
- `priority` - только `"low"`, `"medium"` или `"high"`, по умолчанию `"medium"`.

Файлы:
- `src/data.js` - только данные (`demoTasks`, `variantNumber`, `variantTasks`), логики никакой.
- `src/task-service.js` - все 9 функций и две внутренние проверки (`idIsOk`, `checkTitle`), которые я вынес, чтобы не копировать одну и ту же проверку в разных местах. Ничего не выводит и не хранит список сам.
- `src/main.js` - собирает всё вместе: берёт данные, вызывает функции, печатает результат. Сам поиск/фильтрацию не переделывает.
- `checks.js` - выданный преподавателем файл с 35 проверками + 3 мои в конце.

Функции создания/изменения возвращают `{ ok: true, task/tasks: ... }` при успехе и `{ ok: false, error: "..." }` при ошибке. Функции чтения (`findTaskById`, `getPendingTasks`, `getTaskTitles`, `getTaskStats`) отдельного объекта ошибки не возвращают - это не требуется по заданию.

**Почему id не равен индексу:** индекс это просто позиция в массиве, а id - метка самой задачи. Если удалить задачу из середины, у оставшихся задач индексы сместятся, а id останутся прежними. Поэтому искать надо через `find`, а не `tasks[id]`.

**Почему getTaskStats возвращает число, а не строку с процентом:** потому что округление - это уже про то, как показывать результат, а не про сам расчёт. Если один раз округлить внутри функции, дальше уже нельзя точно посчитать что-то ещё (например, суммарный прогресс по нескольким спискам). Округление через `toFixed(1)` делается в `main.js`, прямо перед выводом.

**Какие объекты копируются при изменении задачи:** новый массив (через spread `[...tasks]` для добавления, через `map` для изменения/удаления) и новый объект той самой задачи, которую меняем (`{ ...task, completed }` или `{ ...task, title }`). Остальные задачи в массиве не трогаются и используются те же самые объекты, что были в исходном массиве.

## 9. Вывод

По сравнению с ПР1 данные теперь не отдельные переменные, а объекты в массиве, а вся логика (создание, поиск, изменение) вынесена в отдельные функции в `task-service.js`, которые ничего не выводят, а только возвращают результат - вывод отдельно делает `main.js`. Для чтения списка использовал `find`/`filter`/`map`, для изменения - spread у массива и у объекта задачи. Неизменность входных данных проверена и через `checks.js` (там есть проверка 33 с `Object.freeze`, плюс мои собственные случаи), и вручную - в `main.js` в конце обоих сценариев выводятся исходные `demoTasks`/`variantTasks`, и видно, что они не поменялись. Основная ошибка, которую пришлось чинить - пропущенный `return` в стрелочной функции из эксперимента 2 (задание 1): без него функция с телом в `{}` возвращала `undefined` вместо числа.

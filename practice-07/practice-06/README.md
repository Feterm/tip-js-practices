## 1. Цель работы

Связать браузерное DOM-приложение с учебным HTTP API: перенести клиент из ПР5, добавить `POST`, `PATCH` и `DELETE`, вывести состояния `loading`, `ready`, `empty`, `error`, проверять форму до отправки и защитить интерфейс от устаревших ответов. В результате задачи и категории приходят с сервера, фильтры уходят в query-параметры, а данные создаются, редактируются, меняют статус и удаляются через API.

## 3. Реализация

### 3.1. HTTP-клиент

`src/api-client.js` - решение ПР5, расширенное параметрами `method` и `body`:

- допустимы только `GET`, `POST`, `PATCH`, `DELETE`; метод приводится к верхнему регистру, остальные дают `TypeError` до запроса;
- `GET` с `body` отклоняется до сетевого запроса;
- в каждый запрос добавляется `Accept: application/json`; при наличии `body` объект превращается в строку через `JSON.stringify` и добавляется `Content-Type: application/json`. Без тела `Content-Type` не добавляется (иначе лишний CORS preflight и неверное описание запроса);
- сохранены тайм-аут (`AbortSignal.timeout`) и внешняя отмена (`AbortSignal.any`), поэтому `timeout` и `aborted` различаются;
- сначала обрабатывается HTTP-ошибка (`ApiError` вида `http` со `status`, `code`, `details`, `url`), потом `204` (возвращается `null`, `response.json()` не вызывается), потом `Content-Type` и разбор JSON;
- `try` стоит только вокруг вызова `fetchFn`, поэтому HTTP-ошибка не превращается в `network`.

### 3.2. Доменный API

`src/task-api.js` содержит `getTasks`, `getTaskById`, `getCategories`, `loadInitialData` (из ПР5, параллельно через `Promise.all`) и новые `createTask`, `updateTask`, `setTaskCompleted`, `deleteTask`, `resetDemoData`. Последний аргумент каждого метода - `{ signal }`.

- `createTask` отправляет в теле только `title`, `priority`, `categoryId`: `id` и `completed` назначает сервер;
- `updateTask` и `setTaskCompleted` используют `PATCH /tasks/:id`, `setTaskCompleted` отправляет `{ completed }`;
- `deleteTask` ожидает строго `null` (ответ `204`), иначе `invalid-response`;
- `resetDemoData` делает `POST /debug/reset` без тела и проверяет `reset === true` и `total`;
- схема ответа проверяется в одном месте: `isTask`/`isCategory`, уникальность id и `meta.total === data.length` для коллекций, форма одиночной задачи для `POST`/`PATCH`/`GET /tasks/:id`; нарушение даёт `ApiError` `invalid-response`;
- локально проверяются только `id` (положительное целое) и фильтры; содержимое черновика задачи проверяет клиентская форма и сервер.

### 3.3. Состояния интерфейса

`src/app-controller.js` не обращается к `document` и работает только через переданные `api` и `view`.

```text
start / applyFilters / refresh / мутация
        -> loading
        -> запрос (первый раз loadInitialData, дальше getTasks)
        -> ready (есть задачи)  |  empty (задач нет)  |  error (messageForError + кнопка повтора)
```

- `empty` - нормальный результат фильтра: список скрыт, показано сообщение, счётчик равен 0;
- `error` показывает понятное сообщение (`messageForError`), кнопка повтора вызывает `refresh()`;
- если категории ещё не получены (первая загрузка не удалась), повтор снова вызывает `loadInitialData`, иначе форма осталась бы без категорий;
- ошибка вида `aborted` пользователю не показывается.

### 3.4. Изменение данных

Все мутации идут через одну внутреннюю функцию `runMutation`:

```text
setMutationPending(true) -> запрос -> notify(success) -> повторный GET с текущими фильтрами -> setMutationPending(false) в finally
```

- создание и редактирование: `submit(draft)` сначала вызывает `validateTaskDraft`; при ошибках запрос не отправляется, ошибки показываются у полей. При успехе форма возвращается в режим создания;
- `toggleTask(id)` инвертирует `completed` через `setTaskCompleted`; `deleteTask(id)` удаляет задачу (подтверждение запрашивает DOM-адаптер) и выходит из режима редактирования, если удалялась правимая задача;
- пока идёт мутация, кнопки заблокированы, повторный вызов игнорируется; блокировка снимается в `finally`, поэтому ошибка не оставляет кнопки заблокированными;
- после успешной мутации список всегда запрашивается заново с текущими фильтрами: так интерфейс показывает подтверждённое сервером состояние, а выборка (например, исчезновение задачи из фильтра) определяется сервером.

### 3.5. Защита от устаревшего ответа

Два механизма в `loadCurrentTasks`:

1. перед новой загрузкой предыдущий `AbortController` отменяется (`activeLoad.abort()`), а новому запросу передаётся его сигнал;
2. каждая загрузка получает номер `loadSequence`; результат (и ошибка) применяется только если номер совпадает с последним.

Второй механизм нужен, даже если есть отмена: источник данных может завершиться, не отреагировав на сигнал (например, подмена `api` в тестах, как в проверке 27). Отмена - обычное управление потоком, поэтому её ошибка `aborted` не показывается.

Форма: `src/form-validation.js` нормализует название (`trim`, 1–100 символов), проверяет приоритет и переводит `categoryId` из строки `select` в число (только цифры, категория должна быть в загруженном списке). `src/task-view.js` строит карточки `li.task-card` с `data-task-id`, тремя кнопками и выводит все строки с сервера через `textContent`.

### 5.2. Браузерные проверки

`http://127.0.0.1:5506/checks.html`:

```text
Всего: 14. Пройдено: 14. Ошибок: 0.
```

**Исправление в готовой проверке.** С исходным `checks/browser.checks.js` проверка «Корректная форма создаёт задачу с серверным id» падает у любой корректной реализации: функция `waitFor` вызывает условие `requireNode(doc, '[data-task-id="35"]')` сразу после отправки формы, а `requireNode` бросает исключение, если элемента ещё нет (запрос на сервер не успел завершиться). Исключение вылетало из `waitFor` вместо ожидания. Из-за этого незавершённый `POST` ещё приходил на сервер уже после сброса данных следующей проверкой, и падала ещё и соседняя проверка («Ошибки формы…»: 13 карточек вместо 12). Я изменил только `waitFor`: исключение от условия перехватывается, и функция продолжает ждать до тайм-аута. Ожидаемые результаты проверок не менялись. Изменение:

```diff
-    const value = condition();
-    if (value) return value;
+    let value = null;
+    try {
+      value = condition();
+    } catch {
+      // Элемент может появиться позже: пока он не найден, продолжаем ждать.
+    }
+    if (value) return value;
```

С исходным `waitFor` итог был «Всего: 14. Пройдено: 12–13. Ошибок: 1–2».

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**
   Сервер получил запрос и ответил, то есть HTTP-обмен прошёл успешно; `404` - это содержимое ответа, а не сбой доставки. Promise отклоняется только при сетевой ошибке или отмене. Поэтому статус проверяется явно через `response.ok`.
2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?**
   У `204 No Content` нет тела, а `response.json()` на пустой строке бросает `SyntaxError`. Клиент возвращает `null` до чтения JSON.
3. **Чем состояние `empty` отличается от `error`?**
   `empty` - запрос успешен, но результатов нет (нормальный итог фильтра): сообщение без кнопки повтора. `error` - запрос не удался: сообщение об ошибке и кнопка повтора.
4. **Зачем отменять предыдущий запрос при смене фильтров?**
   Чтобы старый, более медленный ответ не перезаписал результат нового фильтра и не тратились ресурсы. Дополнительно номер запроса защищает от ответа, который всё же пришёл.
5. **Почему после мутации список повторно запрашивается у API?**
   Сервер - единственный источник истины: только он знает, что после изменения попадёт в выборку с текущими фильтрами (например, выполненная задача исчезнет из фильтра «В работе»). Локальная правка массива могла бы разойтись с сервером.

## 7. Вывод

Браузерный интерфейс, клиентский модуль и контракт API связаны через слои: `dom-app.js` только читает форму и рисует, `app-controller.js` управляет состояниями и мутациями, `task-api.js` знает маршруты и схему ответов, `api-client.js` отвечает за HTTP и виды ошибок. Благодаря этому поведение проверяется в Node.js без DOM, а сервер остаётся источником данных. Найден и исправлен дефект ожидания в готовой браузерной проверке (см. 5.2). Основные риски, которые закрыты: потеря статуса `204`, подмена HTTP-ошибки сетевой, устаревший ответ при быстрой смене фильтров, блокировка кнопок без `finally`.

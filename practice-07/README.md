## Результат

Приложение «Задачи на React» хранит 12 задач и 3 категории в состоянии React (данные в памяти страницы). Поддерживаются:

- вывод задач с названием категории, приоритетом и статусом;
- создание и редактирование с проверкой полей (ошибки показываются сразу у всех неверных полей);
- переключение статуса и удаление после подтверждения;
- совместные фильтры: поиск, статус, приоритет, категория (условие И) и кнопка сброса;
- статистика по всему набору (всего / выполнено / в работе) и счётчик найденных задач;
- пустое состояние выборки и сообщение о результате каждого действия.

Ограничение хранения в памяти: при перезагрузке страницы состояние компонента `App` создаётся заново из `data.js`, поэтому восстанавливаются исходные 12 задач и начальный фильтр варианта. Это ожидаемое поведение ПР7: сохранение между сессиями появится при подключении API в ПР8.

## Компоненты и состояние

| Данные | Владелец | Как меняется |
|---|---|---|
| `tasks` | `App` (`useState`) | Только через `setTasks(previous => …)` и чистые функции `addTask`, `updateTask`, `toggleTask`, `removeTask`. |
| `filters` | `App` | Через `onChange` из `TaskFilters`; сброс возвращает четыре пустые строки. |
| `editingId` | `App` | `onEdit(id)` ставит id, сохранение/отмена/удаление этой записи возвращают `null`. |
| `notice` | `App` | Текст в области `role="status"`. |
| draft и errors | `TaskForm` (локальное состояние) | `onChange` полей, `validateTaskDraft` при отправке. |
| `categories` | импорт из `data.js` | Только читается. |

**Передача данных.** Вниз передаются props: `App` → `TaskStats` (`stats`), `TaskFilters` (`filters`, `categories`), `TaskForm` (`categories`, `initialTask`), `TaskList` (`tasks` - уже отфильтрованные, `categories`) → `TaskItem` (`task`, `categoryName`). Вверх действия поднимаются обратными вызовами: `TaskItem` вызывает `onToggle(task.id)`, `onEdit(task.id)`, `onDelete(task.id)`, `TaskFilters` - `onChange(nextFilters)`, `TaskForm` - `onSave(value)` и `onCancel()`. Дочерние компоненты props не меняют.

**Производные данные** `visibleTasks = selectTasks(tasks, filters)`, `stats = getTaskStats(tasks)` и `editingTask` вычисляются при каждом рендере прямо в `App`. Отдельных `useState`/`useEffect` для них нет, поэтому список, форма и статистика не могут разойтись.

**Неизменяемые обновления.** Чистые функции из `domain/task-service.js` не меняют аргументы: `map` заменяет запись новым объектом `{ ...task, … }`, `filter` удаляет, `[...tasks, task]` добавляет. Если id не найден, возвращается тот же массив. Исходный набор заморожен (`Object.freeze`), поэтому случайная мутация сразу вызвала бы ошибку; состояние создаётся копиями записей.

**Ключи.** В списке `key={task.id}`: id стабилен при удалении и фильтрации, индекс массива в такой ситуации переприсвоил бы состояние не тем элементам. В варианте с вычислением следующего id используется максимум по полному массиву плюс 1 внутри `setTasks(previous => …)`: функция остаётся чистой, а `confirm` и `setNotice` вынесены за пределы функций обновления (это важно в `StrictMode`, где функции обновления вызываются дважды).

**Сброс формы.** `TaskForm` получает `key={editingId ?? 'new'}`. При смене ключа React создаёт форму заново, и `useState(initialTask)` считывает новую задачу, а черновик предыдущей не переносится. После успешного создания форма очищается сама (`onSave` вернул `true`); после редактирования `App` возвращает `editingId = null`, ключ меняется на `'new'`. Если `onSave` вернул `false`, форма показывает `role="alert"` и сохраняет введённое.

## Контрольные вопросы

1. **Чем JSX отличается от строки HTML?** JSX - синтаксис, который компилируется в вызовы создания React-элементов. Это выражения JavaScript: можно вставлять значения через `{}`, использовать `className`, `htmlFor`, закрывать все теги. Текст при этом экранируется, а не разбирается как HTML.
2. **Чем props отличаются от состояния?** Props передаются родителем и не меняются дочерним компонентом; состояние принадлежит компоненту и меняется через `setState`, вызывая повторный рендер.
3. **Почему изменение обычной переменной не заменяет `useState`?** Компонент - функция, при каждом рендере локальные переменные создаются заново, а присваивание не запускает рендер. `useState` хранит значение между рендерами и перерисовывает компонент.
4. **Когда нужна функциональная форма обновления?** Когда новое значение зависит от предыдущего (`setTasks(previous => …)`), чтобы не использовать устаревшее значение из замыкания.
5. **Почему нельзя менять объект задачи внутри поверхностной копии массива?** Копия массива содержит те же ссылки на объекты; изменение объекта изменит и прежнее состояние, React может не заметить изменений, а старые данные испортятся.
6. **Зачем списку стабильный `key`, почему индекс не подходит?** По ключу React сопоставляет элементы между рендерами. При удалении и фильтрации индексы смещаются, и состояние/DOM достанутся не тем записям. `task.id` не меняется.
7. **Почему выборка и статистика не хранятся в состоянии?** Это вычисляется из `tasks` и `filters`; дубли пришлось бы синхронизировать после каждого действия, и они рано или поздно разошлись бы.
8. **Как дочерний компонент сообщает родителю о действии?** Вызывает функцию, полученную в props (`onToggle(task.id)`), а родитель меняет состояние.
9. **Что делает поле управляемым?** Значение берётся из состояния (`value`/`checked`), а `onChange` его обновляет.
10. **Почему `categoryId` из `select` требует преобразования?** Значение HTML-поля всегда строка, а в данных `categoryId` - число; для сравнения и сохранения его нужно привести к числу (с проверкой, что это целое).
11. **Как меняется состояние формы при изменении её ключа?** React размонтирует старую форму и монтирует новую, с новым начальным состоянием `useState`.
12. **Почему подтверждение удаления не внутри функции обновления?** Функции обновления должны быть чистыми и в `StrictMode` вызываются дважды; `confirm` - побочное действие и показал бы окно дважды.
13. **Как отличить отсутствие задач от отсутствия совпадений?** По статистике: при `Всего: 0` задач нет вообще; при `Всего > 0` и `Найдено: 0` совпадений с фильтрами нет.
14. **Что проверяет `npm test` и чего не проверяет?** Чистые функции домена: валидацию, фильтры, статистику, операции без мутаций. Не проверяет React-компоненты, рендер, события и сборку.
15. **Что менять для подключения API в ПР8?** Заменить локальные `setTasks` на асинхронные вызовы `task-api.js`; сделать `onSave` асинхронным (Promise вместо `true`/`false`); добавить состояния загрузки и ошибки, начальную загрузку (`useEffect`), серверные фильтры и повторную загрузку после мутаций.

## Вывод

Освоено разделение интерфейса на функциональные компоненты, хранение общего состояния в `App`, управляемые формы, неизменяемые обновления массивов и вычисление производных данных во время рендера. Исправлены типичные ошибки: сравнение `'false'` как булева значения, преобразование `categoryId` через `parseInt`, сброс формы через `key`. При подключении API в ПР8 потребуется сделать сохранение асинхронным, добавить состояния загрузки и ошибок и перенести фильтрацию и обновление списка на сервер.

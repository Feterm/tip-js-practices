## Эксперимент с очередями выполнения

Файл `examples/event-loop.js`.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | A, B и C - синхронный код (вызов `demonstrateAwait()` выполняется синхронно до первого `await`, поэтому B раньше C). D и E - микрозадачи: обработчик `.then` поставлен в очередь раньше, чем продолжение после `await`, значит D раньше E. F - задача таймера, она идёт после всех микрозадач. |
| Фактический результат | A, B, C, D, E, F | Совпал с прогнозом. |

Фактический вывод исходного примера (до добавления G):

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

- К синхронному коду относятся A, B (тело `async`-функции до первого `await`) и C.
- В очередь микрозадач попадают D (обработчик `.then`) и E (продолжение после `await null`).
- Таймер с задержкой `0` не выполняется сразу: его обработчик ставится как отдельная задача и может сработать только после завершения текущего синхронного кода и всех микрозадач.
- Если удалить обработчик D, порядок остальных меток не изменится: A, B, C, E, F (то же с G в версии с моим обработчиком: A, B, C, E, G, F).

Собственный эксперимент (пункт 6 задания 2): в `examples/event-loop.js` после вызова `demonstrateAwait()` добавлен ещё один обработчик `Promise.resolve().then(() => log("G: мой обработчик Promise"))`.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, G, F | Микрозадачи выполняются в порядке постановки в очередь: D (поставлена первой), E (поставлена при `await null` внутри `demonstrateAwait()`), G (поставлена после вызова функции). Таймер F остаётся последним. |
| Фактический результат | A, B, C, D, E, G, F | Совпал с прогнозом. |

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP-сервер (не менялся). |
| `src/api-client.js` | Транспорт: `ApiError`, `buildUrl`, `createApiClient.requestJson`. Строит URL, делает `GET`, различает виды ошибок, проверяет `Content-Type` и разбирает JSON. Про задачи ничего не знает. |
| `src/task-api.js` | Предметный слой: маршруты `/tasks` и `/categories`, проверка фильтров до запроса, проверка схемы ответа, `loadInitialData` через `Promise.all`. |
| `src/variant.js` | Данные варианта 2: `variantNumber = 2`, `variantFilters = { completed: true }`. |
| `src/main.js` | Готовый консольный сценарий: вызывает `loadInitialData` и отдельно ловит ошибку для задачи `999`. |

**Почему `fetchFn` передаётся в `createApiClient`:** так модульные проверки подставляют поддельную функцию и работают без сети: можно вернуть заранее подготовленный `Response`, сымитировать сетевой отказ или зависший запрос. Интеграционный набор отдельно проверяет настоящий API.

**Почему HTTP-ошибки проверяются отдельно от сетевых:** `fetch` отклоняется только когда ответа нет (сеть, отмена). Ответ `404` или `503` - это нормальный `Response`. Если обернуть в один `try` и `fetch`, и обработку ответа, то созданный после `fetch` `ApiError` с видом `http` попал бы в общий `catch` и ошибочно стал бы `network`. Поэтому `try` стоит только вокруг вызова `fetchFn`.

**Почему JSON после разбора всё равно проверяется по контракту:** `JSON.parse` гарантирует только синтаксис. Значение `{"data":"не массив"}` - корректный JSON, но приложение на нём сломается. Поэтому `task-api.js` проверяет форму ответа и превращает нарушение в `ApiError` вида `invalid-response`.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `new URL(baseUrl)`; допускаются только `http`/`https`, query и hash запрещены (`TypeError`). Лишние `/` на стыке убираются при соединении `baseUrl` и `path`. | Модульные 01, 04 |
| Кодирование query-параметров | `url.searchParams.set(name, String(value))`; пропускаются только `undefined`, `null` и `""`, поэтому `false` и `0` сохраняются. Входной объект не меняется. | Модульные 02, 03; собственная С1 |
| Заголовок `Accept` | `headers: { Accept: "application/json" }` в каждом запросе. | Модульная 05 |
| Проверка `response.ok` | После получения `Response` сначала обрабатывается `!response.ok`: `ApiError` вида `http` со `status`, `code`, `details`, `url` из `payload.error`. Если тело не JSON - сохраняется вид `http` и числовой статус. | Модульные 08, 09, 16 |
| Проверка `Content-Type` | Для успешного ответа (кроме `204`) заголовок должен содержать `application/json`, иначе `invalid-response`. | Модульная 10; интеграционная 11 |
| Разбор JSON | `await response.json()` в отдельном `try`; `SyntaxError` сохраняется в `cause`. Статус `204` возвращает `null` без чтения тела. | Модульные 06, 07, 11 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)` передаётся в `fetch`; при срабатывании `kind: "timeout"`. | Модульная 14; интеграционная 12 |
| Внешняя отмена | `AbortSignal.any([внешний, таймаут])`; если сработал внешний - `kind: "aborted"`. Различение идёт по состоянию сигналов (`signal.aborted`, `timeoutSignal.aborted`), а не по тексту ошибки. | Модульная 15; интеграционная 13; собственная С4 |

## Доменный модуль задач

Фактические результаты при запущенном API:

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id `[4, 13, 34]` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `1 - Учёба`, `2 - Проект`, `3 - Организация` |
| `loadInitialData({ completed: false, priority: "high" })` | `{ tasks, categories, meta }`: задачи `[4, 13, 34]`, 3 категории, `meta.total = 3` |

Правила проверки:

- **Задача:** `id` - положительное безопасное целое; `title` - строка, после `trim` от 1 до 100 символов; `completed` - boolean; `priority` - `low`/`medium`/`high`; `categoryId` - положительное безопасное целое.
- **Категория:** `id` - положительное безопасное целое; `name` - строка, после `trim` от 1 до 100 символов.
- **Коллекция:** `data` - массив; все элементы проходят проверку; `id` не повторяются; `meta` - объект и `meta.total === data.length`; для задач `meta.filters` - объект.
- **Фильтры (до запроса):** разрешены только `completed` (boolean), `priority`, `categoryId`, `q` (строка до 100 символов после `trim`); неверное значение или неизвестный ключ дают `TypeError` без запроса.

## Последовательная и параллельная загрузка

`npm run example:timing`: два запроса `/debug/delay?ms=300`, три запуска.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 635 | 606 | 607 | Время складывается: примерно 2 × 300 мс плюс накладные расходы. |
| `Promise.all` | 305 | 304 | 303 | Запросы идут одновременно, время близко к самой долгой задержке (300 мс). |

Причина разницы: во втором случае оба Promise создаются до общего `await`, поэтому оба запроса уже отправлены. Первый вариант не начинает второй запрос, пока не завершится первый. Точные значения зависят от компьютера, поэтому я не утверждаю, что ускорение всегда будет таким же. Кроме того, `Promise.all` сам ничего не запускает и не отменяет: если один Promise отклонится, итоговый отклонится, а второй запрос продолжит выполняться.

## Вывод

Реализован клиент для учебного HTTP API: общий `api-client.js` отвечает за транспорт и ошибки, `task-api.js` - за маршруты задач и проверку схемы. Все 18 + 26 + 13 проверок проходят, вариант 2 даёт id `[1, 10, 16, 25, 31]`.

Различия, которые я для себя зафиксировал: ожидание Promise - это ещё не результат, а обещание его получить (`await`); HTTP-ошибка - сервер ответил статусом вне 2xx, `fetch` при этом не отклоняется; сетевая ошибка - ответа нет совсем; неверный ответ сервера - статус 2xx, но неподходящие `Content-Type`, JSON или схема; тайм-аут - сработал сигнал `AbortSignal.timeout`; явная отмена - вызывающий код сам вызвал `abort()`. Эти случаи различаются полем `kind` у `ApiError`, а не текстом сообщения.
